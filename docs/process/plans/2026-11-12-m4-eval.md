# tenant-baselines Milestone 4 Implementation Plan: the detection eval

**Goal:** A labelled synthetic replay of five weeks runs through the same Flink job as pre-built minute aggregates, all 12 detector settings side by side; a script scores the alert log, applies the week-4 selection rule and writes `docs/results.md` from 5 official seeds at three seasonality strengths; `make check-paths` proves the aggregates path and the events path give the same alert log.

**Architecture:** Python simulates every request of the eval world with numpy (seeded per stream), aggregates each minute with the job's p95 bucket scheme, places the pre-registered scenarios and writes their labels. A thresholds script fits the static opponents on those same aggregates. Each run gets its own Kafka input topic, `<run>.aggregates-in`; the job reads it in a new bounded `aggregates` mode that skips `MinuteAggregator` and shares everything from `PopulationBaselines` on. Scoring reads `eval.alerts` back from Kafka in event time. A small driver enforces the seed protocol: dev seeds only until a freeze commit, then each official run once, logged.

**Tech stack:** unchanged. No new dependency: the Wilson interval is a closed form, and percentiles come from numpy.

**Spec:** `docs/process/specs/2026-11-09-tenant-baselines-design.md` (v2, approved). Milestone 4 is §8 item 4. Read §3, §4.1–§4.9, all of §5, §7, §8 and §10 before starting. Follow-ups folded in come from `docs/process/m3-followups.md` ("Milestone 4", items 1–12), `m2-followups.md` ("Milestone 4") and `m1-followups.md` ("Before milestone 4 runs a second job on the cluster", "When the code is next touched").

**Budget:** 22–26 hours, against §8's "~8 h"; accepted by the owner on 2026-11-12. About 18 h is the case with no surprises: Tasks 1–5 (job prerequisites and aggregates mode) about 5.5 h; Tasks 6–12 (generator, thresholds, scoring) about 7 h; Tasks 13–16 (driver, check-paths, dev runs, report) about 3.5 h; Tasks 17–19 about 2.5 h, most of it waiting on the official runs. The rest is for what is likely to go wrong: replay mode's first run under load (Task 14), the Scorer's cost with 12 settings (Task 15), and a first bounded source on the cluster (Task 13). **One possible extra loop is not in the figure:** if the owner amends §5.2 or §4.3 at the freeze stop, the dev runs and the report are redone on the amended model before the freeze (about 2 h, Task 17). §8's figure did not count the follow-ups from three reviews (about 3 h here) or the protocol guards.

## Global Constraints

- Everything in the milestone 1–3 plans' Global Constraints still applies.
- Java package root `io.github.sanchaypahalwani.tenantbaselines` (written `<pkg>`). Java builds and tests run only through `make` (`make test-java`, `make jar`); there is no host JDK. Python: `make test-py && make lint-py`.
- **§5.4's scenario table is pre-registered and is not edited.** Magnitudes, counts and eligibility are copied into `scenarios.py` verbatim. Placement details the table leaves open are listed below as builder's calls; none changes a row.
- **Seed protocol (§5.3, owner's call).** Dev seeds are `7`, `11` and `13` *(§9: values are the builder's)*. Until the freeze commit (Task 17) no other seed is simulated for a run. `eval_run.prepare` refuses a dev run with a seed outside that list; `eval_official` refuses to start without `eval/freeze.json`, with a dirty working tree, or for a `(seed, amplitude)` already in `docs/results/official-runs.jsonl`.
- **No detector constant and no grid changes in this milestone.** The grids are §4.6's: seasonal `k ∈ {3, 4, 5, 6}` (settings `k3`…`k6`), static percentiles `{99, 99.9, 99.97, 99.99}` (settings `p99`, `p99.9`, `p99.97`, `p99.99`), mirrored `{1, 0.1, 0.03, 0.01}` for volume. If dev results look wrong, the implementer finds where code disagrees with the spec, or stops and reports. Changing a setting to improve a dev number is the anti-goal in §2. The dev-seed results table goes to the owner at the freeze stop, and only the owner may amend §5.2 or §4.3 on it (owner's decision, 2026-11-12).
- **Detector names:** `seasonal`, `per_key_static`, `global_static`. A detector name has no `/` and a threshold set may not be called `seasonal` (Task 2).
- **Builder's calls on aggregates mode** (each with its reason):
  - Input topic `<run>.aggregates-in`, **one partition**, rows in `(minute, key index)` order. *One split keeps every key's minutes in order with no alignment to reason about.*
  - Each row's event timestamp is `minute_ms + 59_999`, and the watermark strategy is `forMonotonousTimestamps()`. *That is the timestamp `MinuteAggregator`'s timer gives its output in events mode, so `RegionGrouper`'s timers land on the same minute ends in both modes (`m3-followups` item 2).*
  - The source runs at parallelism 1, and the job does not write `<ns>.aggregates` in this mode. *A second subtask would have no split; and re-publishing about 3 million input rows per run would only fill ClickHouse.*
  - A malformed aggregate row fails the job. *A bounded eval must not skip input silently.*
  - Zero-count rows: a key has one row for every minute from its first request to `replay_end − 60_000`. The generator raises if a key is silent for 7 days or more (the eval worlds have no such key), instead of modelling expiry. *`MinuteAggregator` zero-fills exactly this range when no key expires (`m3-followups` item 3).*
- **Kafka timestamps** *(builder's call)*: `eval.*` and `bench.*` output topics and every per-run input topic are created with `message.timestamp.type=LogAppendTime`. *The broker then stamps records with the append time, so retention counts wall-clock age and not the replay's event time. `retention.ms=-1` would also keep the rows, but it would keep every run's output for ever on a laptop volume.* Python producers never pass `timestamp=`. The `live.*` topics are not changed in this milestone (the same loss there affects the forwarder's rebuild from the start of `live.alerts`; it goes on the milestone 5 list).
- **Scoring reads Kafka, not ClickHouse** *(builder's call)*: the driver notes `eval.alerts`' end offset before the submit and reads from there to the new end once the job is `FINISHED`. The read fails unless it is complete: start at or after the low watermark, contiguous offsets, as many records as `end − start`. *No wait on ClickHouse's consumer, and both `absorbed` rows of a twice-absorbed alert survive (`m3-followups` item 12). ClickHouse still ingests `eval.alerts` for Grafana.*
- **Alert log normal form** (used for scoring and for every comparison): drop `emitted_at_ms` and `run_id`; drop exact duplicates; drop rows with `event_time_ms > replay_end_ms`; sort by `(event_time_ms, region, detector, setting, signal, key, state, alert_id)`. Compare parsed values, never JSON text (`m3-followups` items 1, 5).
- **Builder's calls on scoring (§5.5):**
  - A page is a `firing` row. It belongs to week *w* when `starts_at_ms` is inside the week. "Fires" means `event_time_ms` for both scopes (`m3-followups` item 6): a page matches a scenario when `start ≤ event_time ≤ end + 10 min` and it is on an affected key, or it is a regional alert of a region that holds an affected key. Delay is `event_time − start`.
  - A regional page matches every scenario with an affected key in its region whose window it falls in, a tenant-level scenario included.
  - **Recall for the selection rule and the headline is expected-signal recall** *(owner's decision, 2026-11-12)*: a scenario counts when a matching page is on its expected signal. Any-signal recall is reported beside it everywhere.
  - A page that matches no should-page scenario on any signal is a false page, including one during a should-not-page scenario. False pages per day = false pages / 7.
  - Re-fires of a scenario = matched pages beyond the first for the same `(scope, key, signal)`.
  - Percentiles of delays are nearest-rank, reported with their `n`.
  - An alert still open at the replay end is counted as a page like any other; the summary also reports how many rows the clip dropped and how many alerts were open.
  - The "curve" of §5.6 is a table of points per setting, not an image. *No plotting dependency.*
- **Builder's calls on the traffic model (§5.2) and placement (§5.4)** (fixed here, before any dev run):
  - Timeline: week 1 starts at `EPOCH_MS = 1_767_571_200_000` (Monday 2026-01-05 00:00 UTC, a multiple of `HourOfWeek`'s week). Week *w* is `[EPOCH + (w−1)·W, EPOCH + w·W)`; `REPLAY_END_MS = EPOCH + 5·W`.
  - **The eval world's composition.** §5.2's two sentences do not add up: 24 tenants on 2 shared units per region, or on a dedicated unit (6 tenants), give 18 × 2 + 6 = 42 keys, not "about 60". The world built here has **48 keys**: 3 regions; 24 tenants, 8 homed in each region; 6 shared units and 6 dedicated units; the 18 shared tenants have a key on each of their home region's two shared units (36 keys); the 6 dedicated tenants have their dedicated unit and, as a departure from "or", one key on `<home>-s1` (12 keys). That is 16 keys and 8 tenants per region. No tenant has a key outside its home region. Five tenants (6, 10, 14, 18, 22: two homed in `us-east`, two in `eu-central`, one in `ap-southeast`; 5 of 24 = 21%, 10 of 48 keys) keep the hours of another region's time zone, which is §5.2's "served from a region outside their own time zone". *Reaching 60 would take a third shared unit or cross-region keys, and cross-region keys would put half the tenants partly out of zone. The dedicated tenants' shared key keeps them in the shared units' population.*
  - Key size is per key. Load is the key's own expected rate over its weekday peak, scenario volume included, so a ×3 surge has load 3 and gets the latency the curve gives.
  - Error probability `0.003 + 0.002·load` and latency sigma `0.5` are milestone 1's (`traffic.py`). Unit latency medians are uniform in 60–120 ms.
  - Day factors change at the tenant's local midnight. Bursts do not stack.
  - Fit weeks 1–3 each get one shared-unit error burst and one working-hours dedicated-unit drop, labelled, with the table's magnitudes. *"A few scattered labelled incidents" (§5.3).*
  - Every scenario lies inside its week and ends at least 60 minutes before the week ends. On any one key, two scenarios are at least 120 minutes apart. The Monday-peak labels are exempt.
  - "Night or weekend" is the tenant's local 20:00–07:00 or Saturday/Sunday. "Most of the window" is more than half of the unit's key-minutes. "Working hours" windows lie wholly inside local 09:00–17:00 on a weekday. The holiday's local day lies wholly inside the UTC week.
  - Eligibility reads the expected rate before the scenario's own effect, nuisance included.
  - The creep's "unit's keys ≥ 20 for most of the window" pools the unit's key-minutes; it is not a per-key test. The holiday dip covers the keys served in the region. The widest scenarios are placed first.
  - **The thresholds mask** *(owner's decision, 2026-11-12, amending §4.6)*: every labelled scenario except the Monday peak is masked, launch surges and holiday dips included. The mask covers the scenario's keys from its start to its end + 4 minutes (the 5-minute sum carries it; the 4 minutes are the builder's call).
  - A key needs 1,000 calibration values for a signal to get its own threshold for it; otherwise it uses the global one.
- **Things deliberately not changed here:**
  - `AlertEvent`'s fields (`m3-followups` item 9: it is checkpointed state).
  - The cold-bucket resolve of a firing seasonal volume alert (`m2-followups`). *It needs a key with warm and cold volume buckets at once, which the eval worlds never have: a key is cold in every bucket for two weeks and warm in every bucket after. It moves to the milestone 6 list as a documented behaviour.*
- **Output JSON never contains `NaN` or `Infinity`.** Every operator has a `uid`; existing state names and POJO classes stay.
- **Repo rules:** name no employers, clients, internal systems or companies; Apache-2.0; none of the words spearheaded, leveraged, synergy, cutting-edge, results-driven, passionate; every number in the README or `docs/results.md` comes from a script or a measurement, and estimates are labelled as estimates; synthetic data is labelled synthetic; no claim of production use; `results.md` states that the results test the implementation under the stated traffic assumption and are not evidence about real traffic; commit locally after each task, never push, never create a GitHub repo.

## Review Focus

1. **A family that detects nothing, or pages nothing, in a week.** Expected: precision is reported as `0/0`, delays as empty, pages per detected scenario as "none"; the selection takes the highest-recall branch, and a missing median delay sorts last; nothing divides by zero. Pinned in Task 12 (`test_empty_family_scores_without_error`, `test_selection_when_nothing_reaches_eight`).
2. **A scenario that cannot be placed for some seed or amplitude** (at 12:1 only keys with a peak of 300 a minute or more reach 25 a minute at night). Expected: `PlacementError` naming the scenario, raised before anything is produced; the official driver places all 15 runs before it starts the first. Pinned in Task 8 (`test_placement_error_names_the_scenario`, `test_placement_succeeds_on_twenty_seeds_at_every_amplitude`) and Task 17.
3. **The job restarts in the middle of a run, or the laptop sleeps.** Expected: duplicate alert rows collapse in the normal form; a run that takes more than 30 minutes or leaves `RUNNING` for anything but `FINISHED` is cancelled and marked failed, with no summary; a read of `eval.alerts` with a gap fails instead of scoring a short log. Pinned in Task 12 (`test_normalise_drops_duplicates_and_emitted_at`) and Task 13 (`test_wait_fails_on_restart`, `test_read_range_rejects_a_gap`).
4. **Input rows with a gap, a repeat or a backward step for one key.** The Scorer assumes one row per key per minute, in order, and would mis-score silently. Expected: the driver checks the rows before producing and raises. Pinned in Task 9 (`test_check_rows_rejects_gap_repeat_and_disorder`).
5. **The end of the replay.** Holds released at the final watermark carry an `event_time` past the replay end, a regional alert at or above 25% never resolves, and a key's expiry can fall in the last seconds. Expected: both modes emit the same rows, and scoring clips at `REPLAY_END_MS`. Pinned in Task 3 (`expiresAtTheFinalWatermarkWhenDueBeforeReplayEnd`), Task 5 (`aggregatesModeGivesTheEventsModeAlertLog`) and Task 12 (`test_rows_past_replay_end_are_clipped`).

### Task 2: Validate the thresholds file, reject `|` in event fields, pin the p95 policy

No state, no timers.

**Files:**
- Modify: `detect/ThresholdsFile.java`, `io/EventJson.java`
- Create: `flink-job/src/test/resources/thresholds-test.json`, a copy of today's hand-written `infra/flink/thresholds-demo.json`

**Why the copy:** `infra/flink` is a test resource directory, and those five classes assert on the hand-written levels (`global_static/default`, error rate 0.05). Task 11 regenerates the demo file with other names and levels. After this task only `ThresholdsFileTest.loadsDemoFile` reads the demo file.

**Interfaces (produces):**
- `ThresholdsFile.load(InputStream)` throws `IllegalArgumentException` whose message starts with `thresholds set <detector>/<setting>: ` (or `thresholds set #<index>: ` when either name is missing) for:
  - a missing `detector`, `setting`, `valid_from_ms`, or a level without `fire` or `resolve`;
  - a detector containing `/`, or equal to `seasonal` *(the Scorer's machine ids are `detector/setting/signal`, and `seasonal` is the built-in detector's)*;
  - a name in `global` or in a `per_key` entry that is not a `Signal.wire()` value;
  - a `per_key` key that does not split into three non-empty parts on `|`;
  - a level that is not finite, or with fire and resolve in the wrong order: an UP signal needs `resolve ≤ fire`, `volume_5m` needs `resolve ≥ fire`;
  - `valid_to_ms ≤ valid_from_ms`;

### Task 12: Scoring, Wilson intervals and the selection rule

Pure functions over lists and dicts; no Kafka.

**Files:** Create `py/src/tenant_baselines/scoring.py`, `py/tests/test_scoring.py`.

**Rules** (builder's calls on §5.5, the same as in the Global Constraints; recall per the owner's decision):
- A page is a `firing` row. It belongs to week *w* when `starts_at_ms` is in `[week start, week end)`.
- A page matches a scenario when `start_ms ≤ event_time_ms ≤ end_ms + 600_000` and either it has scope `tenant` and its `key` is one of the scenario's `keys`, or it has scope `region` and one of the scenario's keys is in its `region`. So a regional page matches every scenario in its region whose window it falls in. With `expected_only`, its `signal` must also equal the scenario's `expected_signal`.
- A should-page scenario is `detected_any` when any page matches it, and `detected_expected` when a page on its expected signal does. **The selection rule and the headline use `detected_expected`**; `detected_any` is reported beside it.
- Delay = first matching page's `event_time_ms − start_ms`, in minutes. `delay_min` and `median_delay_min` use the expected-signal pages; `delay_any_min` is kept beside them.
- A page is matched when it matches a should-page scenario on any signal; otherwise it is false. `false_pages_per_day = false_pages / 7`. Precision = `matched_pages / pages`, kept as the two counts.
- Re-fires of a scenario = its matched pages beyond the first for the same `(scope, key, signal)`. `pages_per_detected = matched_pages / detected_any`, or `None` when nothing was detected.
- For a should-not-page scenario, `false_pages_during` counts the false pages that match its window and subject.
- Rows with `event_time_ms > replay_end_ms` are dropped before anything else.
